# Design Document: Apple Photos Library Cleanup and Organization Tool

Introduction

Modern photo libraries on Apple devices can grow to tens of thousands of items, often including many poor-quality or redundant shots that clutter the library. This design document describes a Photo Cleanup and Organizer tool for Apple Photos libraries that will automatically prune unwanted photos/videos and group the rest into meaningful events. The tool’s key functions include:
	•	Deleting blurry photos: Identifying and removing images that are out-of-focus or blurred beyond an acceptable threshold.
	•	Deleting “bad” photos/videos: Removing media with poor lighting, obstructed subjects, accidental captures (like pocket shots), or other low-quality indicators.
	•	Deleting redundant photos/videos: Detecting exact duplicates or near-duplicates and keeping only the best instance(s).
	•	Coalescing similar shots: When multiple photos capture the same subject or scene, retaining just one or two of the best and discarding the rest.
	•	Removing temporary snapshots: Finding media that were likely taken for one-time tasks (e.g. screenshots, whiteboard notes, receipts) and cleaning them up after their usefulness has passed.
	•	Organizing into events: Grouping the remaining photos into “events” or albums labeled by date/location or theme, to give structure to the library.

Design Goals: The tool will automate cleanup while preserving content of artistic or personal value. It should allow both one-click fully automated cleanup and a manual review interface for user approval of deletions. The implementation will be as a native macOS/iOS application using Apple-supported APIs (preferred for stability and App Store compliance). Direct integration with iCloud Photos (bypassing the local device APIs) is considered only if it proves viable and stable (current Apple documentation indicates no public cloud API for Photos ￼). Machine learning (ML) models will be employed for image analysis tasks like blur detection and similarity matching, running on-device for privacy and speed when possible (leveraging Apple’s Core ML and Neural Engine), or using a secure cloud service if necessary for heavy processing. The tool will interface with Apple’s Photos framework (PhotoKit) to access and modify the library; direct file system or database manipulation (the Photos SQLite and Masters files) will be a last resort. All deletions will integrate with Photos’ native Recently Deleted album for easy recovery, ensuring an undo path consistent with the Photos app. Although initially a personal project, the tool will be engineered with best practices to enable potential public distribution, adhering to Apple’s privacy guidelines and providing a polished user experience.

Technology Selection and Justification

Platform and Language: The tool will be developed as a native application for macOS and iOS, primarily using Swift. Swift is the preferred language for Apple platforms due to its performance, safety, and first-class support for Apple APIs. A single codebase using SwiftUI for the user interface can target both macOS and iOS, enabling a consistent design and reducing duplication of effort. The choice of a native app (over a web or cross-platform tool) allows deep integration with the Photos library and use of device ML capabilities.

Library Access API: We will use Apple’s PhotoKit framework (part of the Photos/PhotosUI frameworks) to interface with the user’s photo library. PhotoKit is an Apple-supported API that provides robust access to photos and videos on the device and in iCloud (if the user’s library is synced) ￼. Using PhotoKit ensures we are working through supported channels: it handles permission requests, respects the user’s iCloud settings, and automatically fetches iCloud assets when needed. This is preferable to directly reading the Photos library SQLite database or image files, which is fragile and against App Store guidelines (raw file access could break with library format changes and bypasses user privacy controls). PhotoKit will allow us to fetch assets (PHAsset objects) and perform modifications (like deletions or album creation) within the Apple-provided framework.

iCloud Access: Directly interfacing with iCloud Photos via web APIs or CloudKit is not publicly supported by Apple (the iCloud Photos system is effectively closed off to third-party CloudKit containers) ￼. Therefore, approach (b) – an app that talks to iCloud Photos servers – is not considered viable at this time. All interactions will go through the local device’s PhotoKit API. If the user has iCloud Photos enabled, any changes the app makes (deletions, additions to albums, etc.) will sync to iCloud automatically via Apple’s infrastructure. This approach leverages the device as a bridge to iCloud and avoids handling user credentials or reverse-engineering network calls, which would be unstable and a security risk.

Machine Learning and Image Analysis: For tasks like detecting blurry or poor-quality photos, identifying duplicates, and classifying content, we will use on-device ML as much as possible. Apple’s Core ML and Vision frameworks will be central here. The Vision framework provides tools such as VNGenerateImageFeaturePrintRequest which produces a feature vector (embedding) for an image that can be used to compare image similarity ￼. We will leverage this to detect duplicates and clusters of similar photos efficiently. Vision also offers face detection, text detection (for finding screenshots or documents), and general image classification which can help identify content type. For blur detection, we can use a custom Core ML model or a classical computer vision approach (e.g. variance of Laplacian) to classify images as blurry or sharp; this could be a lightweight model running on-device for quick evaluation of each photo. If certain ML tasks prove too slow on-device (for very large libraries or more advanced aesthetic analysis), we will design the system to optionally offload those tasks to a cloud service. A cloud ML service could run a heavier model (e.g. a deep neural network for aesthetic quality or an advanced duplicate clustering) and return results to the app. However, the preferred default is local processing to maintain user privacy and avoid needing to upload personal photos. Cloud offloading, if provided, will be strictly opt-in and use end-to-end encryption during transit.

Development Libraries and Tools: The app’s UI will likely be built with SwiftUI for a modern, reactive interface that can be shared across iOS and macOS (using Catalyst or multiplatform SwiftUI apps). We will also make use of PhotosUI components where appropriate – for example, PhotosUI provides SwiftUI views for picking photos or viewing a library, which might ease the implementation of the review interface. For data storage of any metadata (like storing computed ML features or user preferences), we can use Core Data or simple local files, though the aim is to avoid storing large amounts of photo data ourselves (since PhotoKit can be queried on demand).

Alternative Approaches Considered:
	•	We considered directly accessing the Photos library file system (masters/originals) and SQLite database. This approach was rejected because it is brittle (undocumented schema), requires the app to have full disk access, and cannot be used on iOS (which sandboxes the Photos library). It’s also against the spirit of Apple’s developer rules for interacting with user data.
	•	We considered building a purely cloud-based solution where the user would upload their entire library to a service which then cleans it. This was deemed impractical due to bandwidth, cost, privacy, and duplication of what iCloud already provides.
	•	Using third-party libraries for duplicate detection (such as open-source image hashing libraries) was also considered. We may incorporate algorithms from such libraries (e.g. perceptual hashing via OpenCV or dedicated tools) if needed, but given that Apple’s Vision feature prints accomplish a similar goal, we will lean on the native solution for better integration and performance on Apple hardware.

The chosen technologies ensure the app is fast, secure, and maintainable. Running on Apple’s frameworks allows us to handle iCloud-synced libraries seamlessly (PhotoKit will fetch remote assets on demand) and to use specialized hardware acceleration (the Neural Engine for Core ML models, GPU for Vision tasks) to handle large photo sets efficiently. The use of SwiftUI and high-level frameworks also positions the project well for future updates and potential App Store distribution.

Architecture Overview

The tool follows a modular architecture with clear separation between the photo library interface, the analysis engine, and the user interface. The diagram below gives an overview of the major components and data flow:

Architecture of the Photo Cleanup and Organizer tool. The app uses PhotoKit to fetch media and metadata from the Photos library (local device library, which may be synced with iCloud). An Analysis Engine (with multiple ML sub-components) processes the images to generate suggestions (e.g. “these are blurry,” “these are duplicates of each other,” “these form an event”). Suggestions are stored and then presented to the user via the UI. In manual mode, the user reviews and confirms actions (deletions or album creations), which the app then applies through PhotoKit (e.g. deleting assets moves them to the Photos app’s Recently Deleted album ￼, and creating event albums updates the library). Changes sync to iCloud if enabled.

Component Breakdown:
	•	Photo Library Access Layer: At the base of the architecture is the Photo Library Access Layer, which uses PhotoKit (PHPhotoLibrary, PHAsset, PHAssetCollection, etc.) to interact with the user’s Photos library. This layer handles fetching all media items (or subsets, based on criteria), retrieving metadata (timestamps, locations, etc.), and requesting image data or thumbnails for analysis. It abstracts whether an asset is local or in iCloud – PhotoKit provides a unified view ￼. When the app needs image pixels (for example, to run a blur detection algorithm), it will request them via PHImageManager which under the hood may download from iCloud if the device doesn’t have the original cached (the request can specify isNetworkAccessAllowed=true). This layer also is responsible for committing changes: e.g. using PHAssetChangeRequest.deleteAssets() to delete items (which moves them to Recently Deleted) ￼, or PHAssetCollectionChangeRequest to create albums and add assets to them.
	•	Analysis Engine: This is the core module that implements the “brains” of the cleanup logic. It contains several sub-components, each responsible for analyzing the library for a specific purpose:
	•	Blurry/Quality Detector: Scans photos to identify those that are likely blurry or of low technical quality. This could use an ML model trained to classify an image as blurry vs. sharp, or a heuristic (for example, compute an edge clarity score by applying a Laplacian filter and measuring variance ￼). Photos with a confidence of blurriness above a threshold are flagged as “blurry candidates.” Similarly, this component can flag other “bad quality” images – e.g., extremely dark or overexposed photos, ones with a thumb covering the lens (detected via unusual color/shape in edges), or very low-resolution images. For videos, the quality check might include detecting if the video is extremely shaky or has poor resolution.
	•	Duplicate/Similarity Analyzer: Uses image similarity algorithms to find redundant photos. The tool will generate a feature vector for each photo (using Vision’s featureprint or a perceptual hash) and cluster or compare these vectors to find groups of images that look the same or very similar. By using VNGenerateImageFeaturePrintRequest, we can spot duplicates “even if they vary slightly” in resolution or edits ￼. Exact duplicates (identical files) can additionally be caught by comparing file hashes or metadata (PhotoKit provides a uniform type identifier or can retrieve image data for hashing). This analyzer will output groups of asset identifiers that are deemed duplicates or near-duplicates.
	•	Similar Scene Coalescer: (In the diagram this is conceptually part of the Duplicate Analyzer, but logically it’s an extension.) This component looks at clusters of photos taken around the same time and place or with very high visual similarity. It’s responsible for deciding which one or two photos in a cluster to keep (the rest being “redundant”). It will use metrics from other detectors: for example, within a set of 10 similar photos of the same pose, it might choose the sharpest photo with the subjects’ eyes open and maybe one more with a slight variation. To do this, it might use face detection (via Vision) to see if people in the photo are blinking or smiling, or use an aesthetic scoring model (like NIMA – Neural Image Assessment – or a simpler brightness/contrast analysis) to rank the images. The highest-ranked images in each set are marked “keepers” and the others marked “redundant.” These recommendations will later be presented to the user as “These photos are very similar – keep X and remove the rest.”
	•	Temporary Content Classifier: This sub-component identifies photos and videos that likely correspond to one-time temporary tasks rather than lasting memories. Examples include screenshots, photos of receipts/documents, whiteboard snapshots, or test videos. We will use a combination of metadata and content analysis for this:
	•	Metadata cues: Photos in Apple’s built-in Screenshots album, or with filename prefixes that indicate a screenshot (on iOS, screenshots are named like IMG_1234.PNG but so are camera photos; however, the Photos app does distinguish screenshots in a smart album). We can query for the “Screenshots” smart album via PhotoKit to get those. Also, images with no camera model (if imported from web) or certain dimensions (screenshots often have the exact screen resolution) can be flagged.
	•	Content cues: Using Vision’s text detection (OCR) to see if an image contains a large amount of text (like a document or presentation slide), which often indicates an informational capture that might be temporary. Also detecting computer screenshots (Vision can recognize UI elements or the presence of status bars, etc., though not explicitly provided, a custom ML model could be trained to classify “screenshot vs photo vs document”).
	•	Location/time cues: If a batch of photos were taken for a project (e.g. a series of whiteboard photos within an hour at work), they might share a common visual theme (white background with marker writing) and occur on a weekday in a work location. This is advanced, but the classifier could incorporate such signals.
The output of this classifier is a list of items suggested for deletion as “temporary.” Since it’s hard to be 100% sure (today’s quick snap could be tomorrow’s fond memory!), these would be presented in a review list for the user to confirm.
	•	Event Clustering: After pruning photos, the remaining set can be clustered into events/albums based on date/time and location. This component will analyze timestamps and geolocation metadata to group photos into chunks that likely represent a single event (e.g. an afternoon picnic on July 4, 2024, or a week-long trip to Hawaii). A simple approach is to sort photos by date and split whenever there’s a gap of say >X hours or a significant location change. All photos within a continuous span (few hours) at roughly the same location become one candidate event. The event can be given a tentative label by using the date range and location: for example, if GPS coordinates are available, do a reverse geocode lookup to find the city or venue name (“Central Park, NYC”) and then label the event “Central Park – July 2024” or if the date is recognized as a holiday (“Christmas 2023”), incorporate that. This is an automated guess; the user can later edit names. Additionally, image analysis could help label events (e.g. detect if it’s a beach vs. mountain vs. birthday party by looking for certain objects like Christmas trees or birthday cakes via Vision’s classification). Those labels would be suggestions that the user can accept or change. The Event Clustering outputs a set of event groupings, each with a list of photo IDs and a suggested name and date range.
All these analysis sub-components feed their results into a Recommendations Store, essentially an in-memory (or temporary on-disk) data structure that consolidates all the findings: which photos are flagged for deletion (and why), which groups of photos are identified as duplicates or similar sets, and what event albums are proposed. This separation of analysis allows the next stage to access a full picture of suggestions.
	•	User Interface (UI) and Review Module: The UI module is responsible for presenting the analysis results to the user and letting them choose how to proceed. The design will support two modes:
	•	Fully Automatic Cleanup: In this mode, the app applies all the suggestions without user intervention (aside from an initial confirmation like “Are you sure you want to clean up 300 photos?”). This mode is for users who trust the algorithm and just want quick cleanup. Even in this mode, safety nets exist: all deletions still go to Recently Deleted (so the user can manually recover from Photos app within 30 days if needed), and the app could optionally produce a summary report of what it did.
	•	Manual Approval (Assisted Cleanup): This is a semi-automatic mode where the app groups the suggestions into categories for the user to review and approve or reject. The UI will list categories such as “Blurry Shots”, “Duplicates”, “Similar Photos”, “Screenshots/Temporary”, and “Events”. The user can click each category to see details. For example, under “Duplicates”, the app might show pairs/groups of photos side by side. Under “Blurry Shots”, it would display a grid of small thumbnails of images detected as blurry.
Example UI from Apple’s Photos app (iOS 16 “Duplicates” album) showing how duplicate photos are grouped and can be merged ￼. Our tool’s interface for redundant photos would be similar: it would present groups of similar images with the option to keep only the best one. In a manual review, the user might see a screen like this for each group and choose which to delete or let the app decide automatically.
The review interface should be intuitive and efficient, allowing the user to make decisions in bulk. Key UX considerations include:
	•	For duplicate/similar groups, highlight the photo deemed “best” (e.g. largest preview or a star icon) and smaller previews of the ones suggested for deletion. The user can toggle any to keep if they disagree with the algorithm.
	•	For blurry/bad photos, since these are usually straightforward, allow “Select All” to trash them, while also allowing inspection of any photo by tapping it (maybe to ensure it wasn’t an important one that happened to be blurry).
	•	For temporary items (screenshots, etc.), list them separately because users might want to double-check those; some screenshots or document photos might be important (tickets, receipts for taxes, etc.).
	•	The event grouping UI would show the proposed albums with representative photo(s) and title. The user can edit the title (e.g. change “Untitled Event – May 5, 2025” to “John’s Graduation Party”). They can also merge events or adjust grouping if the algorithm was slightly off (perhaps offer a timeline view to split or join clusters).
In manual mode, after review, the user will press a “Clean Up” or “Apply changes” button. The UI module will then instruct the Photo Library Access Layer to perform the deletions and album creations as confirmed by the user. Progress bars or counters should be shown as changes are applied, especially if many operations (e.g. deleting hundreds of photos might take some time to process and sync with iCloud).
	•	Undo and Recovery: The app will integrate with Photos’ native deletion recovery. When we delete via PhotoKit, items go to the Recently Deleted album (where they remain for 30 days, or until manually permanently deleted) ￼. We will make this clear to the user (e.g. a note: “Removed items can be restored from Photos > Recently Deleted within 30 days”). If the user wants to “undo” immediately (like they made a mistake in the manual selection), we have a couple of strategies:
	•	Since we batch apply changes, we could implement an “Undo” button that appears right after applying, which would programmatically attempt to restore the items. However, PhotoKit does not provide a direct API to undelete from Recently Deleted (the user normally must do it themselves in Photos). As a workaround, the app could keep track of the Asset local identifiers it just deleted and, if undo is triggered, prompt the user to go restore them manually (or potentially use UI scripting to open Photos to Recently Deleted – but that’s clunky). Given this limitation, our primary undo approach is leveraging Recently Deleted itself as the recovery path. For album creation (events), undo is simpler – the app can offer to delete the created albums if the user is unhappy with the grouping.
	•	In automated mode (no manual review), perhaps implement a “dry run preview” – show a summary “We will delete 150 photos and 20 videos, and consolidate 30 sets of duplicates, resulting in 5GB freed. Proceed?” so the user has one chance to cancel. After execution, if they notice something awry, they still have Recently Deleted as fallback.

Data flow summary: The app will typically follow this sequence in operation:
	1.	Scanning – The app obtains permission to access the Photos library, then fetches metadata of all photos/videos (this can be done efficiently with PhotoKit’s fetch APIs, possibly in portions or using change events if the library is huge). Basic filtering (like finding all screenshots via a fetch from the “Screenshots” smart album, or bursts, etc.) can be done at this stage to target certain analyses.
	2.	Analysis – The various analysis engine components run (mostly in background threads so the UI remains responsive). They produce a list of items to delete and groups to organize. Intermediate data like feature vectors or blur scores may be stored in memory or a temporary cache. If the library is extremely large, we might do this in chunks (e.g. analyze 1000 photos at a time) to manage memory and allow incremental progress display (“Scanning… 2000 of 10000 photos analyzed”).
	3.	Suggestion Aggregation – All results are collated. Conflicting suggestions are resolved (for example, if a photo is both blurry and part of a duplicate set, the app should list it under one category, or simply mark it clearly in both but ensure if the user keeps it in one context, it’s not deleted in another). The end result is a coherent set of recommendations.
	4.	User Review/UI – The user is presented with the findings. In auto mode, this step is minimal (just a confirmation dialog or summary), whereas in manual mode the user can navigate through categorized lists as described.
	5.	Apply Changes – The app executes the deletions and album creations through PhotoKit’s change requests. All deletions go to Recently Deleted (per PhotoKit design ￼), and new albums (events) are created in the user’s library with the selected photos. We ensure to perform these in a PhotoKit performChanges block, which handles the transactions and syncing. If any PhotoKit operation fails (could happen if an asset is unavailable or permission lost), we handle errors gracefully (e.g. present an error message listing items that couldn’t be removed).
	6.	Sync and Completion – If iCloud Photos is on, the changes will sync across the user’s devices via iCloud. The app will monitor PhotoKit’s library change notifications to confirm that changes are reflected (PhotoKit provides callbacks when the library changes, so our app can know when the deletion is fully processed). The user sees a final summary or simply that the cleanup is done.

This architecture ensures a clear separation of concerns: the heavy analysis is done in the engine (which could be tested independently), all user data access/modification goes through the PhotoKit layer (maintaining Apple’s intended data integrity), and the UI remains responsive and user-friendly.

Key APIs and Libraries

Implementing the above design will involve several key APIs and frameworks:
	•	Photos/PhotoKit Framework (Photos.framework on iOS/macOS): This is the primary API for library access. Key classes include:
	•	PHPhotoLibrary: Represents the photo library and is used to perform changes in a transactional way (e.g. PHPhotoLibrary.shared().performChanges with delete or add requests).
	•	PHAsset: Represents an image or video in the library. We’ll fetch PHAsset objects for analysis. From a PHAsset we can get metadata like creation date, location (location property), media type, duration (for videos), etc.
	•	PHImageManager / PHCachingImageManager: Used to request image data or thumbnails for a PHAsset. We’ll use this to retrieve image pixels for the ML analysis. We can request a smaller size image for speed when high resolution isn’t needed (e.g. a medium-size image is enough to evaluate blur). If the asset is only in iCloud, PHImageRequestOptions can allow downloading it.
	•	PHAssetCollection and related classes: Represents albums (including smart albums like Recently Deleted or Screenshots). We will use this to fetch specific groups (like the “Screenshots” album for temporary content). We’ll also use it to create new albums for events (via PHAssetCollectionChangeRequest.creationRequestForAssetCollection).
	•	Recently Deleted handling: Note that PhotoKit does not provide direct control of the Recently Deleted album beyond deletion (which automatically goes there). The StackOverflow discussion confirms that the only way to remove an asset via PhotoKit is through delete, which always places it into Recently Deleted (no immediate permanent delete available programmatically) ￼. This is acceptable and desirable for our purposes (safety net).
PhotoKit automatically works with iCloud Photos: “The framework provides access to photos on the person’s device and in iCloud” ￼, meaning if the user has iCloud Photos, our fetches will include cloud assets and will download data as needed. We must be mindful of not inadvertently downloading the entire library at full resolution (which could be large); instead, use smart strategies like analyzing thumbnails or smaller images first, and only downloading full data if absolutely needed to confirm a deletion.
	•	Core ML (CoreML.framework): We will use Core ML to run our machine learning models on device. This includes models we may train or acquire for tasks like blur detection, photo quality scoring, or content classification (e.g. a model to classify an image as a photo vs screenshot vs document). These models will be integrated into the app as .mlmodel files and compiled to leverage hardware acceleration. For example, a simple blur classifier model could be a small CNN that looks at an image and outputs a probability of it being blurry. Core ML can run this very fast on modern iPhones/Macs. We could also use Core ML for an aesthetic ranking model to help choose best photos among similars.
	•	Vision (Vision.framework): Apple’s Vision provides high-level image analysis that complements custom ML models:
	•	VNGenerateImageFeaturePrintRequest: as mentioned, this generates a feature vector embedding for an image. We can compute a distance (e.g. cosine or Euclidean) between two images’ feature vectors to judge similarity. This is ideal for duplicate and near-duplicate detection ￼. We might use a threshold on this distance or cluster by it.
	•	VNImageSimilarityObservation (related to featureprints) or manually computing distances to find clusters of similar images.
	•	Face detection: VNDetectFaceRectanglesRequest can find faces in images; with VNDetectFaceLandmarksRequest we could even judge if eyes/mouth are open, to avoid keeping a photo where everyone has eyes closed.
	•	Scene classification: Vision has a built-in image classifier (VNClassifyImageRequest) that can label an image with categories (e.g. “snow”, “beach”, “indoors, party” etc.). This might help in event labeling or identifying certain types of content.
	•	Text detection: VNRecognizeTextRequest will let us OCR images for text. We’ll use this in identifying temporary content (if an image has a lot of text, it might be a screenshot or document).
	•	We might also use Vision’s human detection (to see if an image has people, which might imply it has personal value) – e.g., if an image has no people or recognizable subject, perhaps it’s more likely a random snapshot. This could be a weak signal in deciding whether to delete something, but we must be careful not to delete all landscapes or object photos just because no people.
	•	Natural Language / Linguistic Analysis (if needed for labeling): Apple’s NaturalLanguage framework could help if we attempt to name events by analyzing things like associated Calendar events or using known place names. For example, if location coordinates reverse-geocode to “Eiffel Tower, Paris,” we can generate an album name “Paris Trip” or similar. This might involve some string processing but not heavy NLP, so this is a minor aspect.
	•	User Interface Frameworks:
	•	SwiftUI will be used to build the interface, given its ability to create rich lists, grids of images, and buttons declaratively. SwiftUI also works with PhotosUI to display thumbnails via Image(phAsset:someAsset) if using the new APIs, or we can convert a UIImage from PhotoKit into a SwiftUI Image.
	•	We might use PhotosUI.PHPickerViewController (UIKit) or the SwiftUI equivalent for any case where the user might need to pick additional photos (though in our app, we typically use full library access, not a limited picker).
	•	AppKit (macOS): If needed for macOS-specific features (like a menu bar item or drag-and-drop), we might incorporate some AppKit, but SwiftUI on macOS can handle most needs.
	•	Networking (if cloud processing is enabled): If we implement an optional cloud ML service, we would use URLSession or a networking library like Alamofire to securely upload images (or better, smaller compressed versions or just the computed features to reduce data) to a server. The server would run an ML model and send back results (e.g., an API that given an image returns “blurry” or not, or given a set of image hashes returns duplicate groupings). However, building such a server and API is beyond the initial scope – the design keeps it in mind (by modularizing the analysis so it could be swapped out), but the first implementation will focus on on-device analysis.
	•	Data Storage: The app itself doesn’t need a heavy database, but we might use a lightweight storage for user settings (for example, a slider for aggressiveness of deletion, or toggles for which categories to auto-clean). This can be done with UserDefaults for simple settings. If we choose to cache ML features (like image feature vectors) to avoid recomputation on subsequent runs, we could use a small local Core Data store or write to files (mapping asset local identifiers to feature vectors). PhotoKit’s localIdentifier for each PHAsset can serve as a key, though note that those identifiers can change if the library is rebuilt or if items are deleted. It might be simpler to recompute each run or do incremental updates as the library changes, using PhotoKit’s change notifications.
	•	Third-Party Libraries: Where Apple’s frameworks suffice (which is mostly the case here), we will stick to them. But some potential third-party inclusions:
	•	OpenCV (compiled for iOS) for additional image processing (like more advanced blur detection algorithms or perceptual hashing) if needed. But that increases app size and complexity, so we’ll attempt to use Vision/CoreImage first.
	•	Duplicate detection libraries: e.g. phash algorithms or the imagededup logic from Python reimplemented – however, using Vision’s featureprint likely negates the need.
	•	ML Models: If we use a model like NIMA (aesthetic rating) or others, we might get a pre-trained model from open source and convert it to CoreML format. We must ensure any model used has a suitable license for inclusion in a potentially public app. For example, Google’s NIMA paper models could be used for non-commercial or with permission; since this app might be public, we’d either train our own or use permissively licensed models.

In summary, the implementation leans heavily on Apple’s native frameworks for both library management and image analysis. This choice ensures compatibility with the Photos ecosystem and takes advantage of hardware acceleration on Apple devices, which is crucial for scaling to large libraries. It also keeps the app within Apple’s app review guidelines (no private API usage), paving the way for public release.

Implementation Specification

In this section, we detail how each of the major features will be implemented, tying together the technologies and architecture described above into concrete steps and algorithms.

1. Photo Library Scanning and Setup

Upon launch (and once the user grants Photos access permission), the app will fetch the list of assets from the library. This can be done with PHAsset.fetchAssets(with: nil) to get all assets, or segmented by media type if we handle photos and videos differently. For performance, we might fetch in batches (PhotoKit can fetch with a predicate, e.g. by creation date ranges, or simply page through the results). We’ll retrieve basic metadata for each asset:
	•	Unique identifier (localIdentifier).
	•	Type (photo or video), and maybe subtype (like screenshot, if PhotoKit marks it as such – PhotoKit has mediaSubtypes that indicate things like if an image is a screenshot or part of a burst).
	•	Creation date, modification date.
	•	Location (if any).
	•	Duration (if video).
	•	Perhaps a small thumbnail (PHImageManager.requestImage with a small target size) for quick analysis.

We will likely maintain an in-memory list or dictionary of assets to analysis results. We may also immediately filter out certain items from analysis: e.g., if an asset is a favorite (the user marked it with a heart in Photos), we likely want to exclude it from deletion suggestions under almost all circumstances (assuming a favorited photo has personal importance). PhotoKit’s PHAsset has a isFavorite property. Similarly, any asset that’s in the user’s custom albums or shared albums might be considered more important (less likely to be trash). We will take those as signals in the analysis phase (maybe lower the priority of deletion suggestions for such items).

If iCloud Photos is enabled and “Optimize Storage” is on, some full-resolution images may not be on device. We will start by requesting just thumbnails or metadata, which don’t require full downloads. Only if an image is flagged as a deletion candidate and we need to be sure (for example, if it’s borderline blurry or not), or if we need full quality to pick the best among similar, then we’ll request a higher resolution image data. We will do so judiciously to avoid a massive network fetch of the entire library.

2. Blurry Photo Detection

For each photo asset (or at least each photo that isn’t obviously a duplicate or already going to be removed for other reasons), the Blurry/Quality Detector will determine if it’s blurry:
	•	Algorithm: A straightforward approach uses the Laplacian variance method: convert the image to grayscale (using Accelerate/vImage or CoreImage for speed), apply a Laplacian filter to highlight edges, and compute the variance of the resulting pixel values. A low variance means little detail (blurry image), high variance means lots of edges (sharp image). This is a common technique for blur detection due to its simplicity ￼. We will calibrate a threshold (possibly via experiments on example images) to classify blur. This method can be done quickly on a downscaled image (e.g. 800x600 pixels) for efficiency.
	•	Machine Learning alternative: If we find the Laplacian method insufficient (it might not catch subtle focus issues or could be thrown off by noise), we can use a small Core ML model. For instance, a model that takes an image and outputs a “blur score” or a binary blur/not blur. We could train this ourselves using a dataset of sharp and blurry images or possibly find an open model. The Medium article suggests using edge detection features and an SVM classifier ￼ – we can replicate that by extracting edge features (Sobel, etc.) and feeding into a small neural network.
	•	We will also consider other “bad photo” indicators here: extreme low-light grainy photos (we can check if the image’s overall brightness is near black, or ISO metadata if available), or photos that are essentially blank (all one color – sometimes happens if lens was blocked, yielding a black or white image). Such images can be flagged the same way as blurry for deletion.

Output: A list of asset IDs that are likely poor quality. Each will have a confidence or score. We might use that later to let the user sort by confidence or to decide automatically (e.g. only auto-delete if extremely confident). For now, flagged blurry photos will be marked for deletion suggestion.

We also ensure to skip analysis for obviously important photos: e.g. if a photo is favorited or contains a face of a person in the user’s People album (if we have access to that – PhotoKit does not directly expose the People album for privacy, but we could run our own face detection and check if the same face appears in multiple photos, implying it might be a known person. This is complex so initial version might ignore that). At least, we won’t automatically delete anything with a detectable face without user review, unless it’s truly an unusable image.

3. Detecting Duplicates and Redundant Photos

This part will handle both exact duplicates and groups of similar images:
	•	Exact Duplicates: Two photos that are pixel-for-pixel identical or one is a direct copy of the other. These might occur if the user imported the same file twice or edited a photo and saved a copy. PhotoKit doesn’t provide a direct “duplicate finder”, so we implement:
	•	Compute a hash for each image. A strong approach is to use a cryptographic hash (MD5/SHA1) on the image data or a perceptual hash (pHash) that is robust to minor changes. Given the performance constraints, we might not want to hash every full image (could be slow for tens of thousands of photos). Instead, using the Vision featureprint is a two-birds-one-stone solution: images with extremely small distance in feature space are likely duplicates or near duplicates.
	•	Alternatively, PhotoKit’s PHAsset has properties like file name, pixel dimensions, and file size. If two assets share all these, they are very likely duplicates (though not guaranteed). We can use those as quick filters: group assets by (filename, size, creationDate) and if any group has more than one, do a deeper comparison on their data.
	•	Near-Duplicates/Similar Images: Using the Vision featureprint approach:
	•	We create a VNImageRequestHandler for each image (or perhaps use it in batches if possible) and get a VNFeaturePrintObservation. From this observation, we can obtain a vector (usually 256-length or 1024-length, Apple doesn’t document the size but we can treat it opaquely) representing the image’s content features.
	•	We then compare vectors. One efficient method: take one image’s feature vector and compute distance to all others (this is O(n^2) if naive, which for n=10,000 could be 100 million comparisons – too slow). To optimize, we can use clustering or approximate nearest neighbor algorithms. We could also reduce dimensionality (feature vectors might be high-dim).
	•	A simpler but effective approach: Use clustering. We could perform K-means or DBSCAN on the feature vectors to find clusters of similar items. Another approach is to index them in an efficient structure (like an ANN tree or even use the fact that Vision’s featureprint might allow direct distance computation via a built-in method, as hinted by Apple’s examples ￼). For initial implementation, since Apple Photos itself now identifies duplicates internally (iOS 16’s Duplicates album), an alternate route is to query the Duplicates album via PhotoKit – however, Apple doesn’t provide direct access to that “album” in PhotoKit API, it’s an internal smart list. So we do our own as described.
	•	We will likely use a threshold: if the distance between two images’ feature vectors is below a certain value, we consider them similar enough to be duplicates. We will test and tune this threshold. Pairs that are mutual nearest neighbors can form clusters.
	•	Burst Photos / Series: Note that Apple’s Camera marks “bursts” (multiple shots taken by holding the shutter) distinctly, and PhotoKit can identify burst collections via PHAssetBurst. We could leverage that to auto-select the best of a burst (Apple’s Photos already picks a “Key photo” for bursts). If accessible, we might simply use Apple’s choice or at least treat bursts as we treat duplicates – likely recommending to keep just the key photo unless others are significantly different or user might want them.
	•	For our purposes, bursts and any similar series (like someone manually taking 5 shots of a scene) will be handled by the similarity clusters and the coalescing logic below.

Selecting the Best Photo in a Set: Once we have clusters of similar photos, we need to choose which to keep:
	•	If the cluster was formed by exact duplicates, the choice is trivial (they are the same image content). In that case, we might prefer the one with highest resolution or smallest size? Actually for exact duplicates, likely identical resolution. If one is an edited version (say user edited brightness), then the content differs and feature might differ too. True exact duplicates can be merged by just keeping one (the user might not care which, but to be safe we keep the one in the primary library and remove the one perhaps in an imported album). We should present which albums each is in – e.g., if one copy is in an album and the other isn’t, maybe keep the one in the album.
	•	For near-duplicates (same scene): We will implement a scoring system. Factors in the score:
	•	Sharpness (from blur detector).
	•	Faces: if people are present, whether they are smiling or not blinking.
	•	Composition/Quality: possibly use an aesthetic model or simpler metrics like brightness/contrast (not too dark, not overexposed).
	•	If one is a live photo or has a video component vs a still, might prefer the live if quality equal (or vice versa if user prefers still).
	•	If one was marked favorite by user or has edits, that one should be kept over unedited ones (likely user edited the best one).
	•	If one has keywords or title (Photos allows adding metadata) that suggests user cared about it, keep it.
	•	Resolution: if one is a lower resolution version (sometimes happens when you have HDR and non-HDR or a photostream copy), prefer the higher resolution.
	•	After scoring, the highest score image(s) in the cluster are “keepers,” others are “redundant.” If scores are very close or it’s subjective, we can mark more than one as keep. For example, if there are 10 similar photos, maybe suggest keeping at most 2; if the top 2 are almost tied, keep both, unless user wants only one. This can be a preference setting (“keep only best 1 per series” vs “allow up to 2-3 if good”).

Output: A set of duplicate/similar groups with the members marked as either “keep” or “delete.” We’ll use this to present the user with something like “You have 5 sets of similar photos – review them.” or automatically delete the designated ones if auto mode.

4. Removing Photos from Temporary Tasks

Identifying photos that likely fall under this category will involve multiple checks:
	•	Screenshots: Using PHAssetMediaSubtype.photoScreenshot (if available via PhotoKit) or checking the asset’s uniform type (UTI) which might indicate PNG (most camera photos on iPhone are JPEG/HEIC, screenshots are PNG). We gather all screenshots. Many users accumulate screenshots that are not needed long-term. The app could suggest deleting screenshots older than a certain age (e.g. older than 2 months) on the assumption they were for temporary use. This threshold can be user-configurable.
	•	Documents/Whiteboards: If an image has a lot of text (via OCR) or looks like a document scan, we flag it. But we must be cautious: some documents might be important (passport scans, etc.). We might restrict automatic deletion to things like if the text seems to be a Wi-Fi password screenshot or an obvious UI screenshot, etc. Perhaps just list them under “Review: these look like documents or notes”.
	•	Other temporary indicators: Photos taken with the device’s camera that might be temporary – e.g., pictures of a price tag, a serial number, a shopping list. These are hard to algorithmically detect. A possible heuristic: they are often taken, sent (maybe via message), and never viewed again. If we had access to Photo engagement (we don’t directly know if user viewed a photo), we could guess if an image was never edited, not favorited, not shared (sharing is not recorded unless we scrape metadata like if it’s in WhatsApp or so, which we cannot). This is where manual review is important – the tool can gather suspects (maybe by excluding anything with people or pretty scenery, and including those with lots of text or product barcodes etc.) and let the user decide.
	•	Videos for temporary use: e.g., screen recordings or random short videos. If the video is a screen recording (PhotoKit might mark those similarly to screenshots), or very short (a few seconds of nothing), or has no sound and low movement (accidental?), we could include them.
	•	Selfies/working photos: Sometimes people take a photo of themselves to test something or a silly moment not meant to keep. Hard to detect, but if front camera and not saved to any album or shared, might be candidate after some time.

Given the difficulty, the implementation will treat these as a separate category that always requires manual approval. The app might provide filters or search within this category (like “show me all screenshots older than X”).

Output: A list of assets flagged as likely temporary. Possibly sub-categorized (Screenshots vs Documents vs Other). The user interface will likely present these with a suggestion like “You have 50 old screenshots that might be unnecessary. You can delete them to free up space.”

5. Organizing Photos into Events

After deletion candidates are identified, we focus on adding structure to the remaining library via events. Implementation steps:
	•	Clustering by Time/Location: Sort all kept photos by date. Iterate through them, grouping sequentially:
	•	Start a new event cluster when one photo is more than (for example) 6 hours apart from the previous, or if it’s on a different day (this threshold can be tuned; perhaps use a shorter gap for same day, but definitely separate different days unless the user had an event that spanned midnight).
	•	Within the same day, if there’s a large gap (like morning vs evening), that might be two events. Also if location jumps significantly (we can calculate distance between GPS coordinates of subsequent photos; if > say 50 km, clearly a new event if time is also different).
	•	We might merge small clusters if they’re the same theme. But initially, time/location should suffice: e.g., a week-long vacation in one city might result in daily clusters, which the user can merge if desired. Perhaps offer an option “Group multi-day trips into one event” if location is the same.
	•	Naming Events: For each cluster, determine a name:
	•	By default, use a date range: e.g. “March 5, 2025” for one-day events, or “March 5 – 7, 2025” for a multi-day event.
	•	If location data is available for photos in the cluster (and they’re mostly the same place or city), append that: e.g. “Paris – March 2025”. We can use Apple’s CoreLocation geocoding to turn coordinates into a city or venue name. This requires network (unless on-device maps available), so we’ll use it sparingly (maybe geocode one representative photo per event cluster).
	•	If the Vision classifier strongly identifies a theme (many photos labeled “beach” or “snow” etc.), or if a holiday (check dates against a list of holidays), we might label accordingly (“Ski Trip – Jan 2025”).
	•	Ultimately, allow the user to edit these names in the UI because automated naming will not always be perfect.
	•	Creating Albums: Using PHAssetCollectionChangeRequest, we will create a new album for each event cluster, with the chosen name, and add the PHAsset references to it. This will effectively group those photos in the Photos app under that album name. If the user’s library already has some structure (like they made albums), we might avoid duplicating that. Perhaps only create an event album if one of that date range doesn’t already exist. Or create all new and let user reconcile later.
	•	One consideration: Apple Photos already does something conceptually similar in the “Memories” and “Days/Months/Years” views (it shows groupings by time and place). But those aren’t user-defined albums and can’t be easily edited or named by the user. Our tool providing explicit albums for events gives the user tangible organization that they can see in their Albums list.

Output: A set of new album creations. We will only actually create them when the user approves (since album creation isn’t easily undoable except by deletion of the album). The user might choose not to create some suggested albums if they find them not useful.

6. Applying Deletions and Changes

With all decisions made (either automatically by the app in auto mode or by the user in manual mode), the final implementation step is to execute the changes:
	•	We will wrap changes in PHPhotoLibrary.shared().performChanges blocks, as required by PhotoKit for modifying the library. We might do multiple blocks or one big block depending on convenience and memory:
	•	Deletions: We gather all PHAsset references (or their local identifiers) that are to be deleted. Then call PHAssetChangeRequest.deleteAssets(...) on that list. This sends those items to Recently Deleted ￼. We should consider that deleting a large number at once might be heavy; PhotoKit might handle it but we’ll test. Alternatively, delete in chunks of say 100 at a time.
	•	Album/Events creation: For each new album, call PHAssetCollectionChangeRequest.creationRequestForAssetCollection(from: assets, title: "EventName") – this can create the album and add assets in one go. Or create the album first, then separate requests to add assets. We must ensure not to include any asset that was just deleted in the same changeset. It might be wise to do deletions in one changes block and album creation in another, to avoid any weird conflicts (since if we delete and add an asset to an album at same time, not sure how PhotoKit handles that; likely the deletion would remove it from everywhere anyway).
	•	For duplicates merging: We aren’t explicitly “merging” like Apple’s duplicate feature (which picks one and moves others to Recently Deleted). Our approach is essentially the same as deletion of the extras. If we wanted to mimic “merge” by preserving one photo’s metadata onto the other, that’s complex and not needed unless we cared about combining edits or keywords. Simpler: just delete the duplicates we don’t want. The best one remains. If there were differences (say one had a caption and the other didn’t), perhaps we copy the caption from one to the other before deletion to not lose information. That could be a nice touch – PhotoKit allows editing asset metadata via PHAssetChangeRequest (like changing description). So an advanced implementation could merge metadata before removal.
	•	We also remove any empty albums that might exist (if say duplicates or something left an album empty; though in our case we only add albums, not remove user’s albums).
	•	Post-Change: PhotoKit will then asynchronously actually apply these changes. We register for PHPhotoLibraryChangeObserver callbacks to know when it’s done. In the callback, we can check if all intended deletions are now reflected (we could check that those PHAsset are now in Recently Deleted or no longer fetchable from main library). Then we signal completion to the UI (e.g. show “Cleanup complete!”).
	•	Error Handling: Some assets might fail to delete (perhaps if they are protected or currently being synced). We will handle the error from performChanges (it provides a success boolean and an Error). If it fails, we might retry or log which assets failed. However, PhotoKit errors are rare if permissions are correct. One scenario is if iCloud syncing is off and the photo is not downloaded – PhotoKit might attempt to download to delete? Not sure, but likely it can still mark it to delete without full download. We’ll test such edge cases.
	•	Cleanup App Data: If we stored any caches (like feature vectors), we might keep them for next run (to avoid redoing heavy computations). But we should discard any data for assets that were deleted (they’re not useful anymore). We should also possibly store a small log of what was deleted in a local file (just in case the user later wonders, they could consult it – though they can also see Recently Deleted contents). For privacy, this log would stay on device.

7. Considerations for iCloud Photos and Device Sync

Since many users use iCloud Photos, our implementation must gracefully handle that environment:
	•	We enable isNetworkAccessAllowed when fetching images via PHImageManager so that if an image is only in iCloud, it will download. We may want to inform the user if a lot of data needs to be downloaded (perhaps an initial scan that only uses metadata can warn “Some full-resolution images will be downloaded from iCloud for analysis. Continue?” and maybe allow the user to exclude those or only analyze what’s local).
	•	When deletions happen, if iCloud is on, those deletions propagate to all devices. This is fine and intended (the whole point is to reduce clutter everywhere). Same for albums creation.
	•	If the user has an optimized library on a device with limited storage, maybe they’d prefer to run this tool on a Mac that has the full library downloaded. We can note in documentation that running the app on a device with the full originals is faster and avoids network usage.
	•	The app itself does not directly interface with any cloud API; it relies on PhotoKit and the user’s iCloud settings. This ensures we don’t need the user’s iCloud login or any special authentication. We just require Photos permission.

8. Performance and Optimization

Implementing these features on a large library (say 50k photos) requires careful performance considerations:
	•	We will use background threads for analysis (DispatchQueues or OperationQueues). For example, we can have one queue dedicated to ML tasks (to not block the main thread) and perhaps limit concurrency to avoid saturating CPU if the user wants to do other work on the device simultaneously.
	•	For similarity analysis, we might not compute feature vectors for all photos if not needed. Perhaps first filter out obvious cases (blurries to delete, etc.), then among remaining compute vectors. We could also use the fact that computing thousands of feature vectors could be done in batches and even possibly during idle times or as a separate “indexing” phase.
	•	We can employ PHCachingImageManager to cache images as we iterate, which might speed up repeated requests (PhotoKit might cache thumbnails).
	•	Memory: when dealing with images, we will downscale images for analysis to perhaps a max dimension (like 1024px) unless full resolution is needed (maybe for fine detail differences, but that’s rare). This reduces memory and processing time significantly while still capturing key features for our analysis.
	•	On devices with Neural Engine (A12 Bionic and later on iPhone, Apple Silicon on Mac), running Vision and ML is very fast. But on older devices, we might need to be more conservative (maybe allow the user to choose analyzing fewer things or not using ML heavy features).
	•	The first run of the app might take a while to analyze everything. We should communicate progress (e.g. a progress bar “Analyzing library…”). Subsequent runs can be faster if we maintain a cache of analysis results and only analyze new or changed photos. We can use PhotoKit’s change tracking (since iOS 14, PhotoKit has change notifications and even a change history API) ￼ ￼ to update our suggestions incrementally.
	•	We also consider energy impact on mobile devices – perhaps advise the user to plug in if doing a full cleanup on an iPhone, as it will use CPU/GPU for a while.

By following these implementation steps and optimizations, we ensure the tool functions robustly and efficiently, cleaning the library as intended without freezing the app or draining resources unnecessarily.

iCloud Access Feasibility

As mentioned earlier, direct access to iCloud Photos (outside of the device’s local library) is not feasible via public APIs. Apple does not provide a CloudKit container or web service for third-party apps to list or modify a user’s iCloud Photos library ￼. Therefore, our design firmly sticks to using PhotoKit on the user’s device.

Implications of this approach:
	•	The user must run the app on a device that has access to their Photos library (e.g., their iPhone, iPad, or Mac that is signed in with their Apple ID and has Photos enabled). The app cannot, for example, be a standalone cloud service that cleans your library without your device. This is by design for privacy and security – even Apple’s own Photos web app on iCloud.com is limited in functionality compared to on-device, showing Apple’s inclination to keep this data under user control.
	•	If the user has multiple devices, they should ideally run the cleanup on one device at a time and let iCloud sync the changes. It’s not possible for our app to run on a server and act on all photos in iCloud directly.
	•	Stability: Using PhotoKit means we rely on Apple’s sync – which is robust. We avoid any reverse-engineered solutions (some projects like icloud_photos_downloader attempt to simulate a device to fetch photos from iCloud – those are brittle and break when Apple changes their private APIs). Our approach will remain stable across iOS/macOS updates as long as PhotoKit is supported.
	•	In case Apple ever does expose an iCloud Photos API or if this tool needed to manage libraries without a local device (for example, a scenario where a user wants to clean up their library but only has a web browser), that would be a separate future design. For now, the feasibility of iCloud direct access is effectively nil, so we do not pursue it.

One special case to note: Shared iCloud Photo Library (a feature introduced in iOS 16 where a family can have a shared library). PhotoKit does allow apps to access the shared library (the user can toggle if the app sees personal library, shared, or both). Our tool should be aware of this: it might need to clean both the personal and the shared library (with user’s permission). We would implement it by fetching assets from both libraries if available. The same principles apply to the shared library content.

UX Design Considerations for Manual Approval

Designing an intuitive user experience is crucial since we are dealing with potentially deleting user’s precious memories. The UI should build user trust and make the process understandable. Here are the key UX design elements and decisions:
	•	Onboarding & Permissions: The first time user opens the app, explain what it does in simple terms (“We help you clean up duplicate or bad photos and organize your memories into albums”). Clearly request the Photos permission with a rationale (“Needs access to scan your library for duplicates and blurry photos”). If possible, show a screenshot of what the result looks like (to entice the user). This sets expectations.
	•	Initial Scan Progress: After permission, if an analysis is needed, show a progress indicator (“Scanning your library…”). Possibly break it down (e.g., “Detecting duplicates… now checking for blurry photos…”) so user knows it’s doing multiple tasks. If this takes more than a few seconds, provide an estimated time or at least a message not to close the app. This is important so the user doesn’t think it’s hung.
	•	Results Summary (Dashboard): Once analysis is done, present a summary screen. This could be a dashboard with cards or sections like:
	•	“⚠️ 15 blurry photos found”
	•	“🗑 120 photos/videos suggested for deletion (duplicates and others)”
	•	“🖼 5 event albums suggested”
	•	“📂 30 screenshots/temporary items found”
	•	and so on, with a “Review” button for each.
Optionally, an overall “Clean Up All” button for those who want to trust the algorithm fully (this would still likely pop a confirm dialog).
	•	Category Review Screens: For each category of suggested deletions, design the layout to facilitate quick decisions:
	•	Duplicates/Similar: As shown in the Apple example above, grouping the photos by set and letting the user compare. We can have a scrolling list of groups. Each group could have a stack of images or a collage. The one we propose to keep is marked (e.g. with a green check or star) and the ones to delete marked with a red trash icon or so. The user can tap a group to expand and see images larger, swipe between them, and change which are kept/deleted by tapping on them. Perhaps provide a “Keep All” in group if the user feels none should be deleted (which would then essentially mark that group as skip). Also a “Select Best for Me” if they want to trust our choice (which is default anyway).
	•	Blurry/Bad: This could be a simple grid of thumbnails. Likely these are not worth inspecting one by one (if obviously blurry). But user might scroll and ensure none of them is something important. Provide “Select All” by default as checked, and user can uncheck any photo they actually want to keep despite blurriness. Provide a quick preview on tap.
	•	Screenshots/Temporary: Also a grid or list with thumbnails. Perhaps show the screenshot images larger because sometimes text needs to be read. We might integrate an OCR viewer – e.g., if user taps a document photo, show recognized text or a quick look, so they can recall if it was important. This helps them decide to delete or not.
	•	Videos: If we have a category for “unneeded videos” (like duplicates or extremely short ones), we need to allow playback or at least a thumbnail with duration shown, so user can decide.
	•	Events: Show each proposed event as a card: e.g. title “Trip to London – June 2023 (45 photos)”. Possibly a cover photo (maybe the best photo of that event chosen by some heuristic). The user can click to see all photos that will go into that album (just to verify unrelated photos didn’t get lumped together). They can rename the event right there (text field). They can choose not to create a particular album if they think it’s not meaningful (maybe the user already has those in an album, etc.).
	•	Global Actions and Confirmations: On each category screen, have a clear action button (“Delete selected x photos” or “Merge duplicates” etc., and “Create albums” for events). If the user goes category by category, they might commit each, or we let them configure all and then press one final apply. The UX could be either:
	•	One final Apply All after reviewing all categories.
	•	Or apply per category.
We should be careful that if they apply some and not others and leave, it might confuse. Better to gather all decisions then apply together. So likely: Mark everything and then one final “Apply Changes” on the summary screen.
	•	Feedback and Undo: After applying, show a confirmation “Clean up complete! 120 items were moved to Recently Deleted.” Provide an immediate “Undo” button if feasible (as discussed, limited by Photos – perhaps just instruct “to restore, go to Photos > Recently Deleted”). Perhaps open the Recently Deleted album automatically if they click a link, but iOS might not allow an app to deep link into Photos app easily. On macOS, maybe we can applescript Photos to open it, but that’s hacky. Instead, we clearly communicate how to undo manually. For album creation, if they change their mind, they can just delete those albums in Photos (mention that too).
	•	Aesthetic and Clarity: The UI design should follow Apple’s Human Interface Guidelines for consistency. Use familiar icons (trash can for delete, etc.). Possibly use a two-column layout on iPad/Mac (categories list on left, details on right). On iPhone, use a navigation stack (push screens). Use accent colors to distinguish safe vs destructive actions (e.g. red for delete buttons). Use confirmations for destructive actions (“Are you sure you want to delete these 50 photos?” even after they pressed apply, just as a final guard).
	•	Education: The first few times, or via a “Learn More” section, explain how the tool makes decisions. E.g., “We use AI to pick the best photo out of similar ones, but it might not always be perfect. Please review the suggestions.” This manages expectations and encourages the user to double-check at least initially. Over time if they see it’s accurate, they can use auto mode more confidently.
	•	Accessibility: Ensure the interface works with Dynamic Type (scales text), VoiceOver (provide descriptions for images like “blurry photo of a person” – we can even generate an automatic description via Vision), and supports both light and dark modes.
	•	Internationalization: If for public use, localize strings for different languages. Also, consider cultural differences in what might be considered a “bad photo” or how events are named (different date formats, local holiday recognition for event naming maybe).

In summary, the UX aims to make cleaning a photo library feel safe and user-controlled. The user can see what’s being deleted and why, override any choice, and benefit from automation without fear of losing something important. By mimicking some of the patterns users see in the Photos app (like grouping duplicates as Apple now does ￼), the interface will feel familiar. At the same time, offering a more powerful multi-category cleanup sets it apart and provides value beyond Photos’ built-in features.

Privacy and Security

Handling personal photos demands a high standard of privacy and security in the tool’s design:
	•	On-Device Processing: By default, all analysis (ML algorithms for detecting blurs, duplicates, etc.) is done locally on the user’s device. This means the photos and videos do not leave the device at any point during the cleanup process. Not uploading content to a server eliminates risks of interception or unauthorized access to the user’s images. It also aligns with user expectations that their photo library remains private.
	•	Optional Cloud Processing (Security): If the app offers an optional cloud analysis mode (for example, to use a more powerful server-based model), it will be designed with stringent security:
	•	Use HTTPS/TLS for all communication.
	•	Require user login or authentication for the cloud service (or use the user’s iCloud – though leveraging iCloud directly for compute is not straightforward, so likely a separate account system if at all).
	•	Inform the user exactly which photos are being uploaded for analysis and get consent. For instance, “To analyze 10,000 photos for duplicates, your device may upload low-resolution copies to our secure server. Continue?”
	•	Ensure any images or data on the server are stored encrypted and deleted immediately after processing. Possibly use a design where the server doesn’t even store the images, it streams through an ML model and returns results. This avoids accumulation of user data on the server.
	•	We might avoid this complexity entirely in early versions to maintain trust – it’s easier to say “everything stays on your device.”
	•	Photo Library Permission: The app will include the necessary key in its Info.plist (NSPhotoLibraryUsageDescription) with a clear message so the user understands why we need access (e.g., “We need to scan your photos to identify duplicates and organize events. We do not upload or share your photos.”). Apple’s privacy rules require this transparency.
	•	No Unexpected Deletions: The app will never delete or modify anything without the user either explicitly triggering it (in manual mode) or explicitly enabling an auto-clean (and even then, with a confirmation prompt). This prevents any surprises. Users can always opt to just scan and see results, and not delete anything if they choose.
	•	Recently Deleted as Safety Net: By leveraging Photos’ Recently Deleted for removals, we ensure that even if something valuable was marked for deletion, the user has up to 30 days to notice and recover it. We will provide guidance on how to recover if needed. This is more secure than if we permanently deleted files immediately (which would be irreversible).
	•	Data Minimization: The app will not collect extraneous data. We don’t need to collect user’s personal info or even which photos they had, beyond what is necessary for the functionality. If we have an analytics component (for a public app to improve or track usage), it will be anonymized (and ideally, we’d avoid even that initially, or get user opt-in because photo-related data can be sensitive).
	•	Storage of Derived Data: If we store any derived metadata (like feature vectors or thumbnails) in a cache, that cache stays on the device’s sandbox. If the user deletes the app, that cache is deleted by iOS. If we store any user preferences or logs, we ensure they are not accessible to other apps (iOS automatically sandboxes, but on macOS if not App Store, we’ll still keep data in user’s Library folder with proper permissions).
	•	We should consider encrypting any sensitive cache (though our feature vectors likely can’t reconstruct the image, to be safe, but they might still reveal something if stolen). Given the threat model (mostly local device security which the user controls), this might be overkill, but worth a note.
	•	Open Source Components and licenses: Ensure any ML model or library used does not introduce privacy issues (e.g., some libraries may phone home or have telemetry; we’ll avoid those). Also comply with licenses (which is a legal aspect, but part of responsible design especially if public).
	•	App Transport Security: If the app does internet (for cloud or for any map API for geocoding), ensure ATS is enabled (which by default it is, requiring HTTPS).
	•	Beta Testing and Sensitive Data: During testing (especially if using TestFlight or sharing with others), make it clear the app is dealing with real photos. Provide guidance like testing on a smaller subset or a dummy library if they’re concerned, until trust is built. For internal testing, we might use a dummy photo library with synthetic data to avoid any accidental personal data leakage in logs, etc.
	•	Compliance and Review: If we go public, prepare a privacy policy document that explains what data the app accesses (Photos) and that it doesn’t transmit personal data off the device (unless user opts for a cloud feature, which will be detailed). This will be needed for App Store review and user transparency. Apple in recent years also asks apps to fill out a “privacy nutrition label” – ours would indicate we access user content (Photos) but it’s not linked to identity and not transmitted off device in normal use.

In summary, privacy is at the forefront: the tool acts as a personal assistant on your device, rather than a cloud service, ensuring the sensitive content of one’s life (photos and videos) remains under the user’s control.

Deployment Model

The tool is initially intended for personal use by the developer, but we are designing it to allow a future transition to a publicly distributed app. This affects how we plan the deployment and distribution:

For Personal Use (Initial Development):
	•	The app can be run directly through Xcode on the developer’s devices or packaged as a Developer ID-signed app for macOS. There’s more leeway to use certain techniques (like maybe command-line scripts or debug logs) when just for personal use. However, we will keep the implementation as if it were going to be released, to avoid large refactors later.
	•	The developer can use actual photo libraries to test, ensuring the tool meets the needs. Any hard-coded configurations (like thresholds for blur, etc.) can be fine-tuned in this phase.

For Public Distribution (Planned):
	•	App Store (iOS and Mac): The ideal distribution is via Apple’s App Stores. For iOS, this is the only realistic way (aside from ad-hoc or enterprise distribution, which are not for public). For macOS, we could either use the Mac App Store or distribute independently (since macOS allows non-App Store apps).
	•	Mac App Store vs Independent: The Mac App Store route would require sandboxing and following similar rules as on iOS. Our app already is mostly within those rules (Photos library access, network access maybe for geocode, which is fine). One possible issue: if we wanted to directly manipulate the Photos library database (which we are avoiding), that wouldn’t be allowed in sandbox. So sticking to PhotoKit keeps us App Store-compliant. If we distribute outside the App Store, we’d sign it with Developer ID for user trust, but we’d lose the easier reach and auto-update that the App Store provides. The preferred route is Mac App Store for consistency, but we’ll evaluate if any capability is lost (currently, none significant).
	•	We should also consider if making it a universal app (one binary for iOS and macOS via Mac Catalyst or SwiftUI multiplatform) or separate apps. Apple’s PhotoKit and SwiftUI support both, so a single codebase can target both. This would allow us to release an iPhone/iPad version and a Mac version together. Many users would appreciate cleaning up on Mac (with big screen) but some might want to do it on their phone directly, so it’s good to have both.
	•	Pricing model: For now, assume either free or one-time purchase on the store. (Not a design aspect per se, but just to ensure no technical blockers like requiring subscription servers, etc., unless the cloud feature is introduced which might entail subscription for server costs.)
	•	Versioning and Updates: We will use source control (git) during development. For public release, we’ll follow semantic versioning (1.0, 1.1 etc.), and plan for updates especially as new iOS/macOS versions or Photo library changes come. For instance, if Apple adds a new media type or a new smart album, we might update the app to handle that.
	•	Beta Testing: Prior to public release, do a TestFlight beta (for iOS) and invite some users (friends or interested testers). On macOS, we can do a TestFlight for Mac or just direct share a beta build. Feedback from others ensures the app works on different library sizes and content types. This can also catch any App Store guideline issues (like if Apple reviewers flag something about deletion usage or privacy wording).
	•	Potential Limitations: One consideration: Will Apple allow an app that mass deletes photos? Yes, if the user grants permission and initiates it. There are already apps like “Gemini Photos” by MacPaw that did similar cleaning of photo libraries, and Apple’s own Photos suggests deletions (duplicates). So it should be acceptable, but the key is making sure user is in control. We should avoid any behavior that might be seen as too risky or automatic without user consent. Emphasize user confirmation steps in the app flow to satisfy reviewers.
	•	Maintenance for Public Use: We would incorporate analytics (basic, privacy-respecting) to see how the app is used and if any crashes occur (using something like Firebase Crashlytics or Sentry). Also gather user feedback to improve the ML models over time (maybe allow an opt-in to anonymously share data about what the algorithm got wrong, though again, photos are sensitive so we likely won’t collect actual images, but maybe summary statistics or counts).
	•	Scalability: As a publicly used app, we must consider different device capabilities. We’ll test on older phones (maybe last 2-3 generations) to ensure it runs reasonably. If performance is an issue on older devices, we may limit certain features there or require connection to power for full scan.

Distribution of ML Models: If our app includes large ML models, those increase app size. On App Store, the limit for cellular download is high nowadays (maybe 200MB), but we prefer a lightweight app. We might keep models around a few MB by using efficient architectures. Or download models on demand (which would require network and should be done with user consent or in background). Initially, we’ll try to bundle what we need within reasonable size.

Open Source Option: The developer might consider open-sourcing some parts (like the core analysis engine algorithms without the UI) so that the community can contribute or validate the approach. But if intending a commercial or at least closed-source product, then just keep it internal. Still, documenting the design (like this) is helpful either way.

In conclusion, the deployment will start with a personal build, then transition to an App Store-ready app. By using only officially supported APIs and focusing on privacy, we position the app well for a smooth App Store approval and user acceptance. We also ensure that the design is robust enough to handle the demands of a wide user base, yet flexible enough for the developer’s own use-case and experimentation during initial development.
